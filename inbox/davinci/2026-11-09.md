### Prove media availability from canonical paths, then relink and proxy deliberately
- Domain: tool
- What went wrong or got revised: In Cloud project `Off The Top E01 (Copy)`, Resolve exposed the expected camera items but their canonical paths still pointed at a disconnected volume. Clip properties did not reliably label the items offline, so trusting the media-pool state would have left the shorts built from unavailable originals.
- Rule to follow next time: Read every source with `MediaPoolItem.GetClipProperty("File Path")` and test the returned path on disk. Group missing items by replacement folder, call `MediaPool.RelinkClips(clips, folder)` once per folder, and read every path back. When remote originals remain expensive to stream, build timecode-preserving proxies and call `LinkProxyMedia` only after the canonical relink is correct; a proxy refusal on an unused clip is not permission to hide a used clip failure.
- How to check it worked: Native readback showed all 40 camera items and both WAVs off the disconnected path. Thirty-eight used camera items accepted the timecode-preserving proxies; the two failures were B-camera files absent from every source cut. Stills from representative close, wide, and alternate-camera clips showed picture before timeline construction.

### Recover from an unhealthy Aspect mount without treating a zero-byte stub as delivery
- Domain: tool
- What went wrong or got revised: Writes through the mounted Aspect path failed with `ENOSPC` while the local cache volume was nearly full, leaving zero-byte files. After a direct upload created the remote folder, the mount listing lagged even though the Aspect CLI already saw it.
- Rule to follow next time: Write or remux the verified file on a healthy local volume first. Delete only the current job's zero-byte mount stub, then upload the local file with `aspect upload ... --replace`. Use `aspect ls` as the immediate remote readback; treat the mounted directory as eventually consistent and do not recreate a folder merely because Finder or the mount has not refreshed.
- How to check it worked: Forty proxy movies totaling about 3 GB uploaded directly. `aspect ls` listed the new remote folder immediately; the mount exposed the same folder after its delayed refresh. The worker then linked and displayed the proxies in Resolve rather than accepting the upload command alone.

### Make multi-timeline Fusion builds idempotent and restart Resolve on a dead scripting server
- Domain: tool
- What went wrong or got revised: The 28-timeline shorts build crashed Resolve four times, usually during Fusion insertion or rapid `SetCurrentTimeline` calls. Calls against the dead application failed with a misleading `NoneType` callable error, and blindly rerunning could preserve a half-built timeline or duplicate its caption nest.
- Rule to follow next time: Persist a per-timeline completion ledger. On retry, skip timelines that are both recorded complete and contain the expected caption track; delete a same-named crash shell and its caption nest before rebuilding. After a crash, dismiss the problem report, relaunch Resolve, and wait for a fresh `Started script server` log entry newer than the launch before loading the project. Retry that timeline once, save after each completed timeline, and slow current-timeline switching rather than hammering it in a verification loop.
- How to check it worked: The worker recovered twice during the batch and completed seven shorts in four timeline variants each. Native inspection found all 28 named timelines, their expected caption structures, and a saved Cloud project with an empty render queue. One QA still per timeline was generated after construction.
- Promote: no
- Already in lessons/: partial (`resolve-crash-resume-render.md` covers render recovery, not idempotent Fusion/caption timeline construction)

- Domain: tool
